## 一、项目总览

### 1.1 这是什么项目？

fin-api-test 是一个 **API 自动化测试平台**，面向金融业务系统（订单/费用链路）。

项目内同时存在两套体系：

| 体系      | 位置                                  | 形态                    | 用途           |
| ------- | ----------------------------------- | --------------------- | ------------ |
| **旧框架** | 根目录 `api/ flows/ steps/ testcases/` | pytest 代码驱动           | 命令行回归测试      |
| **新平台** | `platform/`                         | FastAPI + Vue3 Web 平台 | 可视化 DAG 拖拽编排 |

**实际部署上线的是新平台**，旧框架保留为本地命令行工具。

### 1.2 技术栈

**后端**：Python 3.12 + FastAPI + SQLAlchemy 2.0 + PyMySQL + Pydantic V2 + Alembic

**前端**：Vue3 (`<script setup>`) + TypeScript + Pinia + Vue Router + Element Plus + Vue Flow（DAG 画布）+ Axios

### 1.3 核心能力

- 接口管理：支持 cURL / HAR / OpenAPI 三种导入方式

- 用例编排：DAG 可视化拖拽，多级分组

- 数据驱动：用例一键生成数据集，改单元格即参数化，一行一执行并行展开；
  三级取值优先级 + 快照保真过滤，Excel 导入导出 / 覆盖合并 / 快照过期检测

- 定时任务：用例按间隔/每日定时执行（APScheduler，可选依赖）

- 测试套件：`case_type='suite'` 串行执行多个成员用例（可跨项目引用、逐成员绑环境）；
  共享变量白名单快照注入下游，逐行配对 / 上游失败阻断 / 套件级汇总通知，三入口统一继承

- 变量传递：`${变量名}` 表达式引擎，跨节点引用，DB 查询内联

- 断言体系：17 种断言类型（JSONPath / HTTP / DB / DB vs 响应交叉），DB 断言支持重试

- 执行引擎：线程池异步执行，失败即停止，结构化报告

- 项目版本：快照 / 对比 / 硬回滚

- 用户权限：JWT 鉴权，admin/member 角色，操作审计

- 企微通知：执行结果推送群机器人

### 3.1 应用入口与启动流程

**文件**：[app/main.py](file:///d:/CODE/PyCharm/pythonProject/fin-api-test/platform/backend/app/main.py)

启动流程：

```
uvicorn app.main:app
  ↓
1. load_dotenv()              ← 必须最先执行，加载 .env 环境变量
  ↓
2. 创建 FastAPI 实例
   - default_response_class=BigintSafeJSONResponse  ← 大整数安全
   - CORS 中间件（白名单从 CORS_ORIGINS 读取）
  ↓
3. @app.on_event("startup") 启动钩子，按顺序执行：
   a. _check_secret_key()         ← 校验 JWT_SECRET_KEY，缺失则拒绝启动
   b. init_db()                   ← 智能数据库迁移
   c. _ensure_default_admin()     ← 无用户时创建 admin/admin123
   d. _cleanup_old_executions(30) ← 清理 30 天前执行记录
  ↓
4. 注册 15 个路由模块
```

**关键点**：

- `load_dotenv()` 必须在 import database/auth 之前，否则读不到环境变量

- `BigintSafeJSONResponse` 会把雪花 ID 等大整数序列化为字符串，防前端精度丢失

### 3.3 认证授权机制

**文件**：[app/auth.py](file:///d:/CODE/PyCharm/pythonProject/fin-api-test/platform/backend/app/auth.py)

**Token 签发（登录）**：

```
POST /api/auth/login {username, password}
  ↓
1. 查 User，检查 locked_until（5 次失败锁 15 分钟）
2. verify_password：pbkdf2_hmac(sha256) 10 万轮 + 随机 salt
3. 成功 → create_token(uid, username, role)
   Token = base64(payload{uid,username,role,exp}).base64(hmac_sha256(secret, payload))
   有效期 7 天
4. 失败 → failed_count+1，达 5 次锁定 15 分钟
```

**Token 验证（每个受保护接口）**：

```
Authorization: Bearer <token>
  ↓
get_current_user 依赖：
  1. HTTPBearer 提取 token
  2. decode_token 验签（HMAC-SHA256）+ 验过期
  3. 按 uid 查 User
  4. 返回 User 对象供路由使用
```

**注意**：虽名为 JWT\_SECRET\_KEY，实际是自实现 HMAC-SHA256 签名 Token，非标准 JWT（规避 Python 3.14 下 passlib/bcrypt wheel 问题）。

**密码强度**：长度 8-64，必须同时含字母和数字。

### 4.2 DAG 拓扑排序与节点执行

**文件**：[app/engine/dag\_executor.py](file:///d:/CODE/PyCharm/pythonProject/fin-api-test/platform/backend/app/engine/dag_executor.py)

#### 拓扑排序（Kahn 算法）

```python
# engine/topo.py · topo_order(dag) —— 模块级纯函数，全仓唯一实现
# 执行顺序（dag_executor）与数据集生成列序（dataset_service）共用同一实现，
# 入队稳定性改一处两边同时生效
# dag = {"nodes": [{"id": "n1"}, ...], "edges": [{"source": "n1", "target": "n2"}, ...]}
# 1. 构建入度表和邻接表
# 2. 从入度为 0 的节点开始（按 id 字典序稳定排序）
# 3. 每轮取出队首，将其后继节点入度 -1
# 4. 入度归零的节点入队，重新排序
# 返回 (order, leftover)
#   order: 拓扑顺序的节点 id 列表
#   leftover: 因环或断链未执行的节点（计入失败统计但不落 StepRecord）
```

#### 单节点执行的 9 步管线

```
┌─────────────────────────────────────────────────────────────┐
│ [1] build_request_body(api)                                 │
│     从 ApiField 组装 body（含 ${} 占位符）                   │
```

### 4.4 表达式引擎

**文件**：[app/engine/expression.py](file:///d:/CODE/PyCharm/pythonProject/fin-api-test/platform/backend/app/engine/expression.py)

#### 支持的语法

| 类别    | 示例                                                 | 说明               |
| ----- | -------------------------------------------------- | ---------------- |
| 变量引用  | `${order_id}`                                      | 从 extracted 取值   |
| 兼容写法  | `${context.order_id}`                              | 同上               |
| 环境变量  | `${env.base_url}`                                  | 从 env\_vars 取    |
| 全局变量  | `${global.xxx}`                                    | 从 global\_vars 取 |
| 内置函数  | `${generate_bl_no(prefix='smoke')}`                | 生成提单号            |
| 时间函数  | `${now(format='%Y-%m-%d')}`                        | 当前时间             |
| 随机函数  | `${random_int(min=1, max=100)}`                    | 随机整数             |
| 字符串函数 | `${upper(s='abc')}` / `${md5(s='abc')}`            | 字符串处理            |
| DB 查询 | `${db.query_value('SELECT...', field='order_id')}` | 数据库取值            |

#### 两种替换模式

**模式 A：整串就是一个** **`${...}`** → 返回原生类型（int/dict/list）

```python
"${order_id}" → 123（int）
"${order}" → {"id": 1, ...}（dict）
```

**模式 B：字符串中内嵌多个** **`${...}`** → 字符串替换

```python
"BL_${bl_no}_END" → "BL_ABC123_END"
```

#### 关键设计：未定义变量保留占位符

```python
if val is None:
    return expr  # 保留 ${xxx} 原样
```

这让 body 可以**多次求值**：

1. 第一次求值：`${order_id}` 未定义，保留 `${order_id}`
2. 前置脚本 `set_field` 把 `order_id` 写入 `extracted`
3. 第二次求值：`${order_id}` 能解析为实际值

#### DB 查询变量 `${db.query_value(sql, field)}`

```
${db.query_value('SELECT order_id FROM sys_order WHERE bl_no=${bl_no}', field='order_id')}
  ↓
1. 解析函数名和参数
2. SQL 提取容错（_parse_kwargs 把无 = 的 value 丢弃，回退正则取第一段）
3. _inject_vars(sql)：把 ${bl_no} 替换为已提取变量值（字符串加引号防注入）
4. db_client.query(sql) 执行
5. 返回第一行 field 字段
```

三个 DB 函数差异：

| 函数                                 | 返回值              | 用途      |
| ---------------------------------- | ---------------- | ------- |
| `db.query(sql)`                    | `list[dict]` 全部行 | 取多行数据   |
| `db.query_one(sql)`                | `dict` 第一行       | 取整行     |
| `db.query_value(sql, field='xxx')` | 标量               | 取单值，最常用 |

- 预处理 bash 的 `$'...'` ANSI-C quoting 语法（shlex 不支持）

- 支持 `--data-raw` / `-d` / `--data` / `--data-binary`

### 4.9 测试套件（跨系统用例链）

**文件**：[app/services/suite\_executor.py](file:///d:/CODE/PyCharm/pythonProject/fin-api-test/platform/backend/app/services/suite_executor.py)

**建模**：套件不是独立实体，而是 `TestCase.case_type='suite'` 的用例——复用用例管理全部矩阵
（分组/复制/定时/批量执行/拖拽排序/项目版本快照回滚）；成员存 `suite_members` 表
（可跨项目引用，逐成员独立绑定环境，按 sort\_order 串行执行；禁止嵌套套件）。

**执行语义**（`run_suite`，由 `runner.run_execution_background` 按 case\_type 分流）：

```
套件主记录(running)
  ↓ 按 sort_order 串行驱动成员
成员 A（如：物流「融资数据」，环境=物流测试）
  1. 数据集行展开（plan_case_expansion，与普通执行同口径）
  2. 每行建成员 ExecutionRecord（suite_execution_id 回链主记录，
     suppress_notify=True 抑制逐条通知）→ DagExecutor(..., suite_vars=注入值)
  3. 每行结束：按 shared_vars 白名单从变量池快照（名单外变量不外泄）
成员 B（如：亿海融「发起融资」，环境=亿海融测试）
  同上；注入值来自上游快照 → ExecutionContext.suite_vars（最高优先级）

逐行配对：上游第 i 行快照 → 下游第 i 次执行；下游行数超出沿用最后有效快照
阻断：上游某行失败 → 下游对应行 blocked（不建执行记录），其余行照常；
      上游整体失败/异常 → 后续成员整体 blocked
兜底：成员用例/环境不存在 → 该成员 failed 报错（引用悬空不崩）；嵌套套件显式拒绝
收尾：主 record.env_id 对齐首成员环境；summary={suite:true, 成员×行层级明细,
      shared_vars 终值}；套件级一条企微汇总通知（send_suite_notify）
```

**共享变量两种模式并存**：套件链内走白名单注入（下游用例 `${bl_no}` 零改动）；
下游用例单独执行时无 suite\_vars，走自身数据集/环境变量，行为与普通执行完全一致。

**项目版本适配**（`crud/versions.py`）：快照携带 `case_type/shared_vars/dataset_id/suite_members`；
回滚重建时跨项目成员 id 原样保留（不在本项目删除范围）、本项目成员经 case\_id\_map 重映射；
删除项目用例前先清理引用它的 suite\_members / test\_schedules / data\_sets
（bulk delete 不走 ORM 级联，NOT NULL 外键会挡路）；数据集与定时任务按原 id/新映射恢复。

## 八、如何修改 Bug

### 8.1 Bug 排查路径

发现 Bug 后按以下路径排查：

```
1. 确定是前端还是后端问题
   - 浏览器控制台报错 → 前端
   - API 返回错误 → 后端
   - API 正常但页面显示异常 → 前端

2. 后端排查
   - 查看后端日志（uvicorn 控制台 / journalctl -u fin-api-test）
   - 定位报错的 router → crud → engine
   - 用 tests/ 下的测试文件验证

3. 前端排查
   - 浏览器 DevTools → Network 看 API 请求/响应
   - Vue DevTools 看组件状态
   - 查看对应 views/ 或 components/ 文件

4. 执行引擎问题
   - 查看 StepRecord 和 AssertionRecord 表数据
   - 对照 dag_executor._execute_node 的 9 步管线排查
   - 检查表达式引擎是否正确解析 ${} 变量
```

### 8.2 常见 Bug 类型与定位

| 症状      | 定位路径                                                                                                                                                            |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 执行用例失败  | 报告 → `StepRecord.err`：`HttpStatusError`=请求本身失败（网络/超时/认证），`BusinessError`=业务 code 非约定码；err 为空则看 `AssertionRecord`（actual vs expected；DB 断言查 SQL 与 `retry_count`） |
| 变量未正确传递 | 查 `context.extracted` → 后置提取的 json\_path / SQL → 引用语法 `${var}` / `${env.x}` / `${db.query_value(sql, field)}`                                                   |
| 请求体组装错误 | 查 `StepRecord.request_body`，对照 4.2 管线排查：字段默认值与类型推断（float → string 避免精度）→ 表达式求值 / 前置脚本写变量 → `coerce_json_strings` / `apply_field_types`                          |
| 数据库连接失败 | `.env` 的 `DB_PASSWORD`（特殊字符已 `quote_plus` 编码）→ 环境 `db_config` → 用「测试连接」功能验证                                                                                     |

### 8.3 修改 Bug 的步骤

1. **dev 分支修改**（不直接改 main），**先写测试复现**（tests/ 下对应文件，域函数配 fake-db 单测）
2. 改代码，`python -m pytest tests/ -q` 验证
3. commit（pre-commit 自动跑 ruff/vue-tsc，与 CI 同口径）→ push dev → 合并 main → CI/CD 自动部署（命令见 10.2）
